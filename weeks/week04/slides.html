Two ways of building types, and you can describe almost any data precisely.

The cash register, with tuples

Problem: a cash register

A register knows each article’s code, name, and price.

A purchase is a list of items: a number of pieces and an article code.

Make the bill: for each item, pieces, name, and line total; plus the grand total.

Your turn. With lists and tuples from Week 3: what types would you use?

Hansen’s model: tuples with names

type ArticleCode = string
type ArticleName = string
type Price = int
type Register = (ArticleCode * (ArticleName * Price)) list
type NoPieces = int
type Item = NoPieces * ArticleCode
type Purchase = Item list
type Info = NoPieces * ArticleName * Price
type Bill = Info list * Price

type Price = int is only a second name for int: an abbreviation, not a new type.

The bill, with tuples

let rec findArticle code register =
    match register with
    | [] -> failwith ("unknown article code " + code)
    | (c, article) :: _ when c = code -> article
    | _ :: rest -> findArticle code rest

let rec makeBill register purchase =
    match purchase with
    | [] -> ([], 0)
    | (pieces, code) :: rest ->
        let (name, price) = findArticle code register
        let lineTotal = pieces * price
        let (lines, total) = makeBill register rest
        ((pieces, name, lineTotal) :: lines, lineTotal + total)

Which int is which?

val makeBill:
  register: (string * ('a * int)) list ->
    purchase: (int * string) list -> (int * 'a * int) list * int

Your turn. In (int * 'a * int) list * int, what does each int mean?

You can only tell by position. Swap two ints by mistake: it still compiles.

We need a way to name the parts.

Records

A tuple with named parts

type Article = { Name: string; Price: int }

let coffee = { Name = "iced coffee"; Price = 45 }
let price = coffee.Price                        // 45
  • type Article = { … } defines a new type
  • { Name = …; Price = … } creates one; F# finds the type from the field names
  • coffee.Price reads a field

Predict: “changing” a record

let promo = { coffee with Price = 40 }   // a NEW record

After this, what is coffee.Price?

Still 45. { coffee with Price = 40 } is a new record: immutable, as always.

Patterns and equality

let describe { Name = name; Price = price } =
    $"{name}: {price} baht"
let same = coffee = { Name = "iced coffee"; Price = 45 }   // true

Compared by content, like tuples. (Not true for ordinary objects in Java or C#.)

Predict: two records, same fields

type Point = { X: float; Y: float }
type Vector = { X: float; Y: float }

let p = { X = 1.0; Y = 2.0 }            // a Vector!
let q : Point = { X = 1.0; Y = 2.0 }    // annotated

What is the type of p?

val p: Vector = { X = 1.0
                  Y = 2.0 }

The type defined last wins. When fields clash, annotate.

The cash register, with records

The types

type Article = { Name: string; Price: int }
type Item = { Code: string; Pieces: int }
type Line =
    { Description: string
      Count: int
      Amount: int }
type Bill = { Lines: Line list; Total: int }
let register =
    [ ("a1", { Name = "iced coffee"; Price = 45 })
      ("a2", { Name = "sandwich"; Price = 39 })
      ("a3", { Name = "water"; Price = 10 }) ]

let purchase =
    [ { Code = "a1"; Pieces = 2 }
      { Code = "a3"; Pieces = 1 } ]

One bill line

let rec findArticle code register =
    match register with
    | [] -> failwith ("unknown article code " + code)
    | (c, article) :: _ when c = code -> article
    | _ :: rest -> findArticle code rest

let makeLine register (item: Item) =
    let article = findArticle item.Code register
    { Description = article.Name
      Count = item.Pieces
      Amount = item.Pieces * article.Price }

item.Code, article.Name, item.Pieces: every value says what it is.

The whole bill

let rec makeLines register items =
    match items with
    | [] -> []
    | item :: rest ->
        makeLine register item :: makeLines register rest

let rec total lines =
    match lines with
    | [] -> 0
    | line :: rest -> line.Amount + total rest

let makeBill register items =
    let lines = makeLines register items
    { Lines = lines; Total = total lines }

Small functions, each easy to test on its own.

Tuples vs records

Tuples Records
a bill line (2, "iced coffee", 90) { Description = …; Count = 2; Amount = 90 }
the bill’s type (int * string * int) list * int Bill
mixing up two ints compiles silently a type error, or visibly wrong
reading a part by position by name

Same logic, now readable, for people and for the compiler.

Rule of thumb: short-lived results, tuples. Anything stored or passed around, records.

Unions: one of several kinds

Problem: shapes

A shape is either a circle, a rectangle, or a triangle.

Your turn. Can you model this with records and tuples? What goes wrong?

Students usually propose a record with a “kind” string and fields for every shape. Ask: what is the radius of a rectangle?

A union type

type Shape =
    | Circle of radius: float
    | Rectangle of width: float * height: float
    | Triangle of a: float * b: float * c: float
let wheel = Circle 0.3
let door = Rectangle (0.9, 2.0)
let sail = Triangle (3.0, 4.0, 5.0)

One of the cases, each with its own data. All three are Shapes.

Problem: the area of a shape

area (Rectangle (0.9, 2.0)) = 1.8

Before the code: how many rules will the match have? What does each one bind?

area: one rule per case

let area shape =
    match shape with
    | Circle r -> System.Math.PI * r * r
    | Rectangle (w, h) -> w * h
    | Triangle (a, b, c) ->
        let s = (a + b + c) / 2.0                // Heron's formula
        sqrt (s * (s - a) * (s - b) * (s - c))

Constructors are patterns: Rectangle (w, h) matches only rectangles, and binds the data.

Forget a case

> let area shape =
      match shape with
      | Circle r -> System.Math.PI * r * r;;

warning FS0025: Incomplete pattern matches on this expression.
For example, the value 'Rectangle (_, _)' may indicate a case
not covered by the pattern(s).

Add | Ellipse of … to Shape next year: every match in the program that misses it gets a warning.

In this course: every FS0025 is a bug.

Predict: month 13

Week 1’s daysInMonth 2025 13 returned 0. Now:

type Month =
    | January | February | March | April | May | June
    | July | August | September | October | November | December

Your turn. How do you write “month 13” now?

You can’t. The problem isn’t handled; it’s removed.

let isLeapYear year =
    (year % 4 = 0 && year % 100 <> 0) || year % 400 = 0

let daysIn year month =
    match month with
    | February -> if isLeapYear year then 29 else 28
    | April | June | September | November -> 30
    | _ -> 31

Each case, its own data

type Payment =
    | Cash of received: int
    | Card of lastFour: string
    | PromptPay of phone: string

let receiptLine total payment =
    match payment with
    | Cash received -> $"Cash {received}, change {received - total}"
    | Card lastFour -> $"Card ending {lastFour}"
    | PromptPay phone -> $"PromptPay to {phone}"

Compare: one record with fields for cash, card, and phone, most of them meaningless.

Types as sets

Counting values

  • |\texttt{bool}| = 2, \ |\texttt{unit}| = 1, \ |\texttt{Month}| = 12

Tuples and records multiply (“AND”):

|A \mathbin{*} B| = |A| \times |B| \qquad |\texttt{bool * Month}| = 24

Unions add (“OR”):

|\;\texttt{C1 of A | C2 of B}\;| = |A| + |B|

Products and sums: algebraic data types.

Problem: a traffic light

// red, amber, green: each lamp on or off
type LampsOn = bool * bool * bool

Your turn. How many values does LampsOn have? How many are real?

2 \times 2 \times 2 = 8 values; only 3 are real. Every function must decide what “red and green” means.

Make illegal states unrepresentable

type Light =
    | Red
    | Amber
    | Green

let next light =
    match light with
    | Red -> Green
    | Green -> Amber
    | Amber -> Red

Exactly 3 values, all real. next has nothing to check.

Count the values; compare with reality. Week 9 builds a whole design method on this.

Option

Problem: no answer

What should each of these return?

  • maximum []
  • lookup "juice" prices, when there’s no juice
  • month number 13

So far: failwith (crash), or a magic value like 0 or -1.

Your turn. What’s wrong with the magic value?

option: just a union

type 'a option =
    | None
    | Some of 'a
let some3 = Some 3                     // int option
let nothing : int option = None

|\texttt{'a option}| = |\texttt{'a}| + 1: every value, plus “nothing”.

Functions that might not answer

let rec tryLookup key table =
    match table with
    | [] -> None
    | (k, v) :: _ when k = key -> Some v
    | _ :: rest -> tryLookup key rest
val tryLookup:
  key: 'a -> table: ('a * 'b) list -> 'b option when 'a: equality

The type says it honestly: you might not get a 'b. By convention: try in the name.

You can’t forget to check

> let x : int = Some 3;;
error FS0001: This expression was expected to have type 'int'
but here has type ''a option'
let priceText item table =
    match tryLookup item table with
    | Some price -> $"{item}: {price} baht"
    | None -> $"{item}: not on the menu"

Forget None, and: FS0025 … the value 'None' may indicate a case not covered.

The antidote to null

null / None / undefined hides inside any variable. Forget to check: NullPointerException, Cannot read properties of undefined. Tony Hoare: his “billion-dollar mistake”.

  1. Absence is in the type. A string is always a string; only a string option might be missing.
  2. You can’t forget to check. No int out of an int option without handling None.
  3. Check once, at the boundary. After the match, the value is plain.

The habit: might have no answer? Return an option. Never a magic value.

Options at the boundaries

let monthFromNumber n =
    match n with
    | 1 -> Some January | 2 -> Some February | 3 -> Some March
    | 4 -> Some April | 5 -> Some May | 6 -> Some June
    | 7 -> Some July | 8 -> Some August | 9 -> Some September
    | 10 -> Some October | 11 -> Some November | 12 -> Some December
    | _ -> None

A number from outside can be invalid: option. A Month inside your program is always valid.

Genuinely optional data

type Person = { First: string; Middle: string option; Last: string }

let fullName person =
    match person.Middle with
    | Some m -> $"{person.First} {m} {person.Last}"
    | None -> $"{person.First} {person.Last}"

The register, without crashing

let rec tryFindArticle code register =
    match register with
    | [] -> None
    | (c, article) :: _ when c = code -> Some article
    | _ :: rest -> tryFindArticle code rest

makeBillSafe bills the known items and returns the unknown codes, instead of crashing mid-sale.

Recursive unions

Problem: a list type from scratch

Every list is [], or x :: rest.

Your turn. Write that as a union type.

MyList

type MyList<'a> =
    | Empty
    | Cons of 'a * MyList<'a>

let rec myLength xs =
    match xs with
    | Empty -> 0
    | Cons (_, rest) -> 1 + myLength rest

Empty is []; Cons (x, rest) is x :: rest. That’s essentially F#’s own list.

The Week 3 recipe was always “one rule per case of the type”. Week 6: trees, the same way.

Nested patterns

let rec sumKnown xs =
    match xs with
    | [] -> 0
    | Some x :: rest -> x + sumKnown rest
    | None :: rest -> sumKnown rest
let rec countBigCircles shapes =
    match shapes with
    | [] -> 0
    | Circle r :: rest when r > 1.0 -> 1 + countBigCircles rest
    | _ :: rest -> countBigCircles rest

One pattern checks the shape and takes it apart, several levels deep.

Beyond F#

Records, unions, and options elsewhere

Records Unions with data Option
Rust struct enum, exhaustive match Option<T>, no null at all
Swift struct enum with associated values T?, compiler-checked
Kotlin data class sealed classes, exhaustive when T?, compiler-checked
Java record (16+) sealed + record, switch (21) Optional<T>
C# record (9+) class hierarchies; built-in unions proposed nullable reference types (8+)
TypeScript object types discriminated unions T | undefined + strictNullChecks
Python @dataclass(frozen=True) A | B hints + match, unchecked Optional[T] hints

The more a language enforces the three rules, the fewer null crashes.

Summary

  • Records: named fields, { x with … }, compared by content; annotate on clashes
  • Unions: one of several cases, each with its own data; constructors are patterns
  • FS0025 names the case you missed: every one is a bug
  • Count values: products multiply, sums add. Design out impossible states
  • option: absence in the type; handle None; never a magic value
  • F#’s list is a recursive union; “one rule per case”
