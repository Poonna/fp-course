Week 4 · Modeling Data: Records, Unions, and Option

Lecture notes

NoteAfter this week you should be able to
  • define record types, build and update records, and take them apart with patterns;
  • define union types (choices), and handle every case with match;
  • use the compiler’s completeness checks to find every place a new case must be handled;
  • count the values of a type, and use the count to spot impossible states;
  • use option for “there might be no answer”, and handle both cases, every time;
  • combine records, unions, lists, and options in nested patterns.

So far, our data has been built from the types F# provides: numbers, strings, tuples, lists. This week we define our own types. With just two ways of building types, records and unions, you can describe almost any kind of data precisely. Many functional programmers consider this the single most useful idea in the whole paradigm, and it has been spreading into other languages quickly.

We start with a problem, and solve it twice.

1 The cash register, with tuples

The problem (adapted from Hansen): A cash register knows, for each article code, the article’s name and price. A purchase is a list of items, each with a number of pieces and an article code. Make the bill: for each item, the number of pieces, the article name, and the total price for that line; plus the grand total.

With the tools from Week 3, we can model this with tuples, and give the types names with type abbreviations:

type ArticleCode = string
type ArticleName = string
type Price = int
type Register = (ArticleCode * (ArticleName * Price)) list
type NoPieces = int
type Item = NoPieces * ArticleCode
type Purchase = Item list
type Info = NoPieces * ArticleName * Price
type Bill = Info list * Price

type Price = int doesn’t create a new type. It only gives int a second name, to make our intentions readable. Here is some data, and the two functions we need:

let register =
    [ ("a1", ("iced coffee", 45))
      ("a2", ("sandwich", 39))
      ("a3", ("water", 10)) ]

let purchase = [ (2, "a1"); (1, "a3") ]
let rec findArticle code register =
    match register with
    | [] -> failwith ("unknown article code " + code)
    | (c, article) :: _ when c = code -> article
    | _ :: rest -> findArticle code rest

let rec makeBill register purchase =
    match purchase with
    | [] -> ([], 0)
    | (pieces, code) :: rest ->
        let (name, price) = findArticle code register
        let lineTotal = pieces * price
        let (lines, total) = makeBill register rest
        ((pieces, name, lineTotal) :: lines, lineTotal + total)

makeBill register purchase gives ([(2, "iced coffee", 90); (1, "water", 10)], 100). It works. But look at the type F# infers for makeBill:

val makeBill:
  register: (string * ('a * int)) list ->
    purchase: (int * string) list -> (int * 'a * int) list * int

Which int is the number of pieces? Which is the price, and which the line total? In (int * 'a * int) list * int, you can only tell from the position of each value, and you have to remember what each position means. Swap two ints by mistake and the program still compiles. Our type abbreviations didn’t help F#, because Price and NoPieces are both just int to it.

What we want is a way to name the parts.

2 Records

A record is like a tuple whose parts have names, called fields:

type Article = { Name: string; Price: int }

let coffee = { Name = "iced coffee"; Price = 45 }
let price = coffee.Price                        // 45
> let coffee = { Name = "iced coffee"; Price = 45 };;
val coffee: Article = { Name = "iced coffee"
                        Price = 45 }
  • type Article = { Name: string; Price: int } defines a new type with two fields. Unlike a type abbreviation, this really is a new type: an Article is not a tuple, and not any other record.
  • { Name = …; Price = … } creates a record. F# works out from the field names that it’s an Article.
  • coffee.Price reads a field.

2.1 “Changing” a record

Records are immutable, like everything else. To “change” one, make a copy with some fields replaced:

let promo = { coffee with Price = 40 }   // a NEW record

{ coffee with Price = 40 } means “a record just like coffee, but with Price = 40”. The original coffee still costs 45.

2.2 Records in patterns

A record can be taken apart with a pattern, naming the fields you want:

let describe { Name = name; Price = price } =
    $"{name}: {price} baht"

The pattern { Name = name; Price = price } binds the two fields to name and price. You only need to mention the fields you use.

2.3 Equality

Records are compared by their contents, field by field, just like tuples:

let same = coffee = { Name = "iced coffee"; Price = 45 }   // true

(This is not true in every language. In Java or C#, two ordinary objects with the same contents are usually not equal unless you write extra code, or use their newer record feature. See Beyond F#.)

2.4 A pitfall: fields with the same names

F# finds the record type from the field names. If two record types have the same field names, it uses the one defined last:

type Point = { X: float; Y: float }
type Vector = { X: float; Y: float }

let p = { X = 1.0; Y = 2.0 }            // a Vector!
let q : Point = { X = 1.0; Y = 2.0 }    // annotated
val p: Vector = { X = 1.0
                  Y = 2.0 }

When field names are shared, say which type you mean with an annotation, as for q. The same applies to function parameters: let makeLine register (item: Item) = … below annotates item so that item.Code is unambiguous. Annotating record parameters is a good habit in any case.

3 The cash register, with records

Now the same problem with named fields:

type Article = { Name: string; Price: int }
type Item = { Code: string; Pieces: int }
type Line =
    { Description: string
      Count: int
      Amount: int }
type Bill = { Lines: Line list; Total: int }
let register =
    [ ("a1", { Name = "iced coffee"; Price = 45 })
      ("a2", { Name = "sandwich"; Price = 39 })
      ("a3", { Name = "water"; Price = 10 }) ]

let purchase =
    [ { Code = "a1"; Pieces = 2 }
      { Code = "a3"; Pieces = 1 } ]
let rec findArticle code register =
    match register with
    | [] -> failwith ("unknown article code " + code)
    | (c, article) :: _ when c = code -> article
    | _ :: rest -> findArticle code rest

let makeLine register (item: Item) =
    let article = findArticle item.Code register
    { Description = article.Name
      Count = item.Pieces
      Amount = item.Pieces * article.Price }

let rec makeLines register items =
    match items with
    | [] -> []
    | item :: rest ->
        makeLine register item :: makeLines register rest

let rec total lines =
    match lines with
    | [] -> 0
    | line :: rest -> line.Amount + total rest

let makeBill register items =
    let lines = makeLines register items
    { Lines = lines; Total = total lines }

Compare the two versions:

Tuple version Record version
a bill line (2, "iced coffee", 90) { Description = "iced coffee"; Count = 2; Amount = 90 }
the bill’s type (int * string * int) list * int Bill
mixing up two ints compiles silently a type error, or visibly wrong code
reading a part a pattern, by position line.Amount, by name

The logic is the same; the records make it readable, both for people and for the compiler. The record version also splits the work into small functions (makeLine, makeLines, total), each of which is easy to test on its own.

TipWhen to use a tuple, when a record

Tuples are fine for small, short-lived groupings, especially function results like (quotient, remainder) or (lines, total), where the meaning is obvious from the context. As soon as a grouping is stored, passed around, or has several parts of the same type, give it a record type with named fields.

4 Unions: one of several kinds

Records say “an article has a name and a price”. Often we need to say “a thing is either this or that”. Hansen’s example: a shape is either a circle, a rectangle, or a triangle.

type Shape =
    | Circle of radius: float
    | Rectangle of width: float * height: float
    | Triangle of a: float * b: float * c: float

This defines a union type (also called a discriminated union, or choice type) with three cases. Each case has a name, called its constructor, and optionally some data. The field names (radius, width, …) are optional documentation. Creating a value means choosing one case:

let wheel = Circle 0.3
let door = Rectangle (0.9, 2.0)
let sail = Triangle (3.0, 4.0, 5.0)
> Circle 2.0;;
val it: Shape = Circle 2.0

> Rectangle (3.0, 4.0);;
val it: Shape = Rectangle (3.0, 4.0)

All three are values of the same type, Shape. So a Shape list can contain circles, rectangles, and triangles together.

4.1 Taking unions apart

Constructors are also patterns. A constructor pattern matches only values built with that constructor, and binds the data inside:

let area shape =
    match shape with
    | Circle r -> System.Math.PI * r * r
    | Rectangle (w, h) -> w * h
    | Triangle (a, b, c) ->
        let s = (a + b + c) / 2.0                // Heron's formula
        sqrt (s * (s - a) * (s - b) * (s - c))

The match has exactly one rule per case: the code follows the structure of the type, just as list functions followed the structure of lists in Week 3. In fact, that is no coincidence (see Recursive unions below).

4.2 The compiler checks every case

This is where match really pays off. Suppose we forget a case:

> let area shape =
      match shape with
      | Circle r -> System.Math.PI * r * r;;

warning FS0025: Incomplete pattern matches on this expression. For example, the
value 'Rectangle (_, _)' may indicate a case not covered by the pattern(s).

F# tells you exactly which case is missing. Now imagine a program with fifty functions that match on Shape, and a new requirement: support ellipses too. Add | Ellipse of a: float * b: float to the type, recompile, and every match that doesn’t handle ellipses gets a warning, pointing to the line. In languages without this check, you find the places you forgot one bug report at a time.

ImportantTreat FS0025 as an error

An incomplete match compiles, but crashes at run time with MatchFailureException when the missing case turns up. In this course, every FS0025 warning is a bug, and labs are marked that way. (Real projects often make the compiler treat it as an error.)

4.3 Unions without data: enumerations

A union’s cases don’t have to carry data. Hansen’s months:

type Month =
    | January | February | March | April | May | June
    | July | August | September | October | November | December

Recall daysInMonth year month from the Week 1 lab, which took the month as an int and had to return 0 for “month 13”. With a Month type, there is no month 13:

let isLeapYear year =
    (year % 4 = 0 && year % 100 <> 0) || year % 400 = 0

let daysIn year month =
    match month with
    | February -> if isLeapYear year then 29 else 28
    | April | June | September | November -> 30
    | _ -> 31

The problem of invalid months hasn’t been handled, it has been removed: an invalid month can’t even be written. (Converting a number from the user into a Month can still fail, of course. We handle that with option, below.)

4.4 Cases with different data

Each case can carry its own kind of data. How a customer pays at the register:

type Payment =
    | Cash of received: int
    | Card of lastFour: string
    | PromptPay of phone: string

let receiptLine total payment =
    match payment with
    | Cash received -> $"Cash {received}, change {received - total}"
    | Card lastFour -> $"Card ending {lastFour}"
    | PromptPay phone -> $"PromptPay to {phone}"

Cash needs the amount received, a card only its last four digits, PromptPay a phone number. With a union, each case holds exactly what it needs, and nothing else. Compare the alternative, a record with a field for each possibility, where most fields are meaningless most of the time.

5 Types as sets: counting values

Week 3 promised to make sense of the * in tuple types. Think of a type as the set of its possible values, and count them. Write |T| for the number of values of type T:

  • |\texttt{bool}| = 2 and |\texttt{unit}| = 1.
  • |\texttt{Light}| = 3, if Light is the union Red | Amber | Green.
  • |\texttt{Month}| = 12.

Tuples and records multiply. A value of bool * Month is a bool and a Month: any of the 2 choices combined with any of the 12, so |\texttt{bool * Month}| = 2 \times 12 = 24. In general

|A \mathbin{*} B| = |A| \times |B|

which is why the tuple type is written with *, like the Cartesian product A \times B. A record with fields of types A and B has the same count. Records and tuples are product types, or “AND types”.

Unions add. A value of a union is one of its cases, so you add up the possibilities of each case:

|\;\texttt{C1 of A | C2 of B}\;| = |A| + |B|

A case without data counts as 1. Unions are sum types, or “OR types”. (Together, product and sum types are called algebraic data types. Now you know where the name comes from.)

5.1 Why count?

Counting reveals impossible states that a type allows. A traffic light has three lamps. Modeled as “which lamps are on”:

// red, amber, green: each lamp on or off
type LampsOn = bool * bool * bool

That type has 2 \times 2 \times 2 = 8 values, but a real light only shows 3 of them. The other 5 (all off, red and green, …) are values your program can create, and every function has to decide what to do with them. The union has exactly the 3 values that exist:

type Light =
    | Red
    | Amber
    | Green

let next light =
    match light with
    | Red -> Green
    | Green -> Amber
    | Amber -> Red

next needs no checks for impossible combinations, because there aren’t any. Good types make illegal states unrepresentable. Week 9 builds a whole design approach on this idea.

6 Option: a value that might not be there

In Weeks 1–3, some functions had no good answer for some inputs:

  • daysInMonth 2025 13 returned 0, a “magic value” that looks like a real answer;
  • lookup for a missing key and maximum [] stopped the program with failwith.

Each time, the notes promised a better way. Here it is. F#’s library defines a small union:

type 'a option =
    | None
    | Some of 'a

A value of type int option is either None (no value) or Some n for some int n. It is an ordinary generic union, no different from the ones we defined above:

let some3 = Some 3                     // int option
let nothing : int option = None
> Some 3;;
val it: int option = Some 3

> None;;
val it: 'a option

Counting its values: |\texttt{'a option}| = |\texttt{'a}| + 1. It is 'a, plus one extra value that means “nothing”.

6.1 Functions that might have no answer

A function that might not have an answer returns an option. By convention, its name starts with try:

let headOpt xs =
    match xs with
    | [] -> None
    | x :: _ -> Some x
let rec tryLookup key table =
    match table with
    | [] -> None
    | (k, v) :: _ when k = key -> Some v
    | _ :: rest -> tryLookup key rest
val tryLookup: key: 'a -> table: ('a * 'b) list -> 'b option when 'a: equality

The type says it honestly: you might not get a 'b. Hansen’s findPos returns the position of an element, if it is there:

let rec findPosFrom i x xs =
    match xs with
    | [] -> None
    | y :: _ when y = x -> Some i
    | _ :: rest -> findPosFrom (i + 1) x rest

let findPos x xs = findPosFrom 0 x xs

findPos 4 [2 .. 6] is Some 2; findPos 7 [2 .. 6] is None.

6.2 Using an option: always both cases

You can’t use an int option as an int:

> let x : int = Some 3;;

error FS0001: This expression was expected to have type
    'int'
but here has type
    ''a option'

To get at the value, you have to match, and the match has to handle None too:

let priceText item table =
    match tryLookup item table with
    | Some price -> $"{item}: {price} baht"
    | None -> $"{item}: not on the menu"

Forget the None case, and F# warns you, just as it did for a missing Shape:

> let get o = match o with Some x -> x;;

warning FS0025: Incomplete pattern matches on this expression. For example, the
value 'None' may indicate a case not covered by the pattern(s).

A very common way to handle None is a fallback value:

let withDefault fallback option =
    match option with
    | Some x -> x
    | None -> fallback

6.3 The antidote to null

In Java, C#, JavaScript, Python, and many other languages, “no value” is usually represented by a special value such as null, None, or undefined, which can hide inside any variable of almost any type. A method that returns a String might return null instead, and nothing in its type tells you. Forget to check, and the program crashes at run time with a NullPointerException or TypeError: Cannot read properties of undefined, often far from where the null came from. Tony Hoare, who introduced null references in 1965, later called them his “billion-dollar mistake”.

option fixes this with three simple rules:

  1. Absence is visible in the type. A string is always a string. Only a string option might be missing, and you can see it in the signature.
  2. You can’t forget to check. There’s no way to use an int option as an int without a match (or a function like withDefault that does one), and the match must handle None.
  3. The check happens once, at the boundary. Once you have taken the x out of Some x, it is a plain value, and the rest of your code never needs to worry about it again.

The habit to build, starting now: whenever a function might have no answer, return an option, and never invent a magic value like 0, -1, or "".

6.4 Options at the boundaries

The places where options appear most naturally are where data enters your program. Turning a user’s number into a Month can fail; after that, the month is always valid:

let monthFromNumber n =
    match n with
    | 1 -> Some January | 2 -> Some February | 3 -> Some March
    | 4 -> Some April | 5 -> Some May | 6 -> Some June
    | 7 -> Some July | 8 -> Some August | 9 -> Some September
    | 10 -> Some October | 11 -> Some November | 12 -> Some December
    | _ -> None

Options also model data that is genuinely optional, such as a middle name:

type Person = { First: string; Middle: string option; Last: string }

let fullName person =
    match person.Middle with
    | Some m -> $"{person.First} {m} {person.Last}"
    | None -> $"{person.First} {person.Last}"

6.5 The cash register, without crashing

Our register’s findArticle stops the whole program on an unknown code. With an option, an unknown code becomes information we can act on:

let rec tryFindArticle code register =
    match register with
    | [] -> None
    | (c, article) :: _ when c = code -> Some article
    | _ :: rest -> tryFindArticle code rest
// Known items become lines; unknown codes are collected, not fatal.
let rec sortItems register items =
    match items with
    | [] -> ([], [])
    | item :: rest ->
        let (lines, unknown) = sortItems register rest
        match tryFindArticle item.Code register with
        | Some article ->
            let line =
                { Description = article.Name
                  Count = item.Pieces
                  Amount = item.Pieces * article.Price }
            (line :: lines, unknown)
        | None -> (lines, item.Code :: unknown)

let makeBillSafe register items =
    let (lines, unknown) = sortItems register items
    ({ Lines = lines; Total = total lines }, unknown)

Now makeBillSafe bills the known items and returns the unknown codes alongside, instead of crashing halfway through a sale. The decision about what to do with unknown codes (ask the cashier, print a warning) is left to the caller, where it belongs.

NoteWhat about several steps that might each fail?

Here each item was handled on its own. When one step depends on another that might fail (look up the article, then check the stock, then apply the discount), the matches start nesting inside each other. Week 8 shows how to chain such steps neatly, and introduces a type that can also say why something failed.

7 Recursive unions

A union case can contain a value of the union itself. Here is a list type, defined from scratch:

type MyList<'a> =
    | Empty
    | Cons of 'a * MyList<'a>

let rec myLength xs =
    match xs with
    | Empty -> 0
    | Cons (_, rest) -> 1 + myLength rest
> Cons (1, Cons (2, Empty));;
val it: MyList<int> = Cons (1, Cons (2, Empty))

Compare it with F#’s own list: Empty is [], and Cons (x, rest) is x :: rest. That is essentially how F#’s list is defined in the library, with special syntax added for convenience. So the recipe from Week 3, one rule for [] and one for x :: rest, is simply the rule “one rule per case of the union”. In Week 6, we’ll define trees the same way, and the same recipe will work for them too.

8 Nested patterns

Patterns fit inside each other, following the shape of the data. An option inside a list:

let rec sumKnown xs =
    match xs with
    | [] -> 0
    | Some x :: rest -> x + sumKnown rest
    | None :: rest -> sumKnown rest

A union case inside a list, with a guard:

let rec countBigCircles shapes =
    match shapes with
    | [] -> 0
    | Circle r :: rest when r > 1.0 -> 1 + countBigCircles rest
    | _ :: rest -> countBigCircles rest

Circle r :: rest matches a list whose first element is a circle, and binds r to its radius. This is what makes match so much more powerful than if: one pattern can check the shape of a value and take it apart, several levels deep, in a single line.

9 Beyond F#

Records have arrived almost everywhere, usually with automatic equality by content:

Language Record-like type
C# (9+) record Article(string Name, int Price); with with-expressions
Java (16+) record Article(String name, int price) {}
Kotlin data class Article(val name: String, val price: Int) with copy(...)
Python @dataclass(frozen=True) classes
TypeScript object types { name: string; price: number } (compared by reference, not content)
Rust struct Article { name: String, price: u32 } with #[derive(PartialEq)]

Unions with data are newer in mainstream languages, but spreading fast. Rust’s and Swift’s enums are full unions: enum Shape { Circle(f64), Rectangle(f64, f64) }, with exhaustive match. Kotlin and Java (17+) use sealed interfaces or classes, whose subclasses are the cases; Java 21’s switch checks them exhaustively. TypeScript has discriminated unions, object types with a common kind field, { kind: "circle"; radius: number } | { kind: "rect"; w: number; h: number }, narrowed by switch. C# has long relied on class hierarchies or libraries for this; built-in unions have been proposed for the language, so check the version you use. Python’s type hints can express unions (Circle | Rectangle), and match can take them apart, but nothing checks that every case is handled.

Option exists nearly everywhere too: Option<T> in Rust (which has no null at all), optionals T? in Swift and Kotlin (checked by the compiler), Optional<T> in Java, nullable reference types in C# (8+; warnings when you might use a null), T | undefined in TypeScript with strictNullChecks, and Optional[T] hints in Python. The more of the three rules above a language enforces, the fewer null crashes its programs have.

10 Going further (optional)

NoteCounting function types

Functions are values too, so we can count them. A function from bool to Light has to choose a Light for true and a Light for false: 3 \times 3 = 9 possibilities. In general |A \to B| = |B|^{|A|}, which is why mathematicians write the set of functions from A to B as B^A. With sums, products, and powers, types really do obey the rules of high-school algebra. For instance, a function taking a pair, A * B -> C, has |C|^{|A| \cdot |B|} values, and so does its curried form A -> B -> C, with (|C|^{|B|})^{|A|}. Currying (Week 2) is the type-level version of the law c^{ab} = (c^b)^a.

NoteSingle-case unions

A union can have just one case: type ArticleCode = ArticleCode of string. Unlike the abbreviation type ArticleCode = string, this is a new type: you can’t pass a plain string where an ArticleCode is expected, or mix up an ArticleCode with a customer’s name. It costs almost nothing, and catches a whole class of mistakes. Week 9 uses this technique extensively.

11 Summary

  • A type abbreviation (type Price = int) only gives a new name; a record or union makes a new type.
  • Records group named fields: { Name = "tea"; Price = 45 }, x.Name, { x with Price = 50 }, patterns { Name = n }. Equality is by content. Annotate when field names clash.
  • Unions describe a choice of cases, each with its own data: Circle of float | Rectangle of float * float. Constructors build values and are patterns.
  • match handles each case; FS0025 names any case you missed. In this course, it’s a bug.
  • Counting values: products multiply, sums add. Use counts to spot impossible states, and design types without them.
  • option (None | Some of 'a) is the honest answer to “there might be nothing”. Absence is in the type; you must handle None; after the match, the value is plain. Never use magic values.
  • F#’s list is a recursive union; the list recipe is “one rule per case”.
