Week 1 · Programs as Expressions

Lecture notes

NoteAfter this week you should be able to
  • run F# code in the interactive environment (FSI) and in script files;
  • read an FSI response and say what name, type, and value it reports;
  • define values and functions with let, and apply functions to arguments;
  • explain why if … then … else in F# produces a value, and predict its type;
  • tell a pure expression from one with a side effect, and say why the difference matters;
  • evaluate a small program by hand, step by step, using substitution;
  • explain what immutability means and why mutation makes programs harder to reason about.

1 Why functional programming?

Most of you learned to program by giving the computer a sequence of instructions: create a variable, change it, loop, change it again. That style is called imperative programming, and it describes how to reach an answer.

Functional programming starts from a different question: what is the answer? A functional program is built mainly from expressions that compute values and functions that turn values into other values. There is much less “change this variable” and much more “this value is defined as…”.

This is not an academic curiosity. The ideas in this course have been flowing into mainstream tools for years:

  • Lambdas, under many names: Java’s lambda expressions, C#’s lambdas and delegates, C++ lambdas, JavaScript’s arrow functions x => x * 2, Python’s lambda. Every callback you have passed to an event handler, a sort function, or a thread is a function used as a value, the most basic idea in functional programming.
  • React components are encouraged to be pure functions of their inputs, and state updates are expected to produce new objects rather than modify old ones.
  • Rust makes variables immutable by default and treats almost everything as an expression.
  • Java, C#, Kotlin, TypeScript, Swift, and Python have all added features such as records, pattern matching, or tagged unions that come straight from functional languages.
  • Java streams, C# LINQ, and JavaScript’s map/filter/reduce are functional collection processing.

We use F# because it lets us see these ideas clearly, without the noise that comes from bolting them onto a language designed for something else. F# runs on .NET, so it can also use the whole .NET library, build web servers, and even compile to JavaScript. We will do all of that later in the course. Everything you learn here, though, is meant to travel with you to whatever language you use next. Each week’s notes end with a short Beyond F# section that makes that connection explicit.

2 Getting set up

You need two things: the .NET SDK and an editor.

  1. Install the .NET SDK (version 10 or later) from Microsoft’s .NET download page. Check it in a terminal:

    dotnet --version

  2. Install an editor. Either works:

    • Visual Studio Code with the Ionide-fsharp extension, or
    • JetBrains Rider (free for non-commercial use).

2.1 The interactive environment (FSI)

F# comes with an interactive environment called FSI (F# Interactive). Start it with:

dotnet fsi

You type an expression, end it with ;;, and press Enter. FSI evaluates it and replies:

> 2 * 3 + 4;;
val it: int = 10

Read the reply from left to right:

  • val means “here is a value”;
  • it is the name FSI gives to the result of the last expression you typed;
  • int is the type of the value;
  • 10 is the value itself.

The ;; is only needed in FSI, to say “I’m done, evaluate this”. You never write ;; in a script file or a program. Type #quit;; to leave FSI.

2.2 Script files

Typing into FSI is great for quick experiments, but anything longer belongs in a script file with the extension .fsx. You can run a whole script from the terminal:

dotnet fsi hello.fsx

In VS Code or Rider you can also select a few lines of a script and press Alt+Enter to send just those lines to FSI. This is the workflow we will use most in the first half of the course: write in a script, send pieces to FSI, look at the replies.

TipMake FSI your habit

Whenever you are unsure what something does, ask FSI. Type it, look at the type and the value. Guessing the reply before pressing Enter, and then checking, is one of the fastest ways to learn a language. Many of this week’s drills work exactly like that.

3 Two ways to describe a computation

Suppose we want the average of three exam scores: 72, 85, and 90. Here is a statement-by-statement version, written in F# but in the style you probably know from C or Java:

// Statement style: create a variable, then change it step by step.
let mutable total = 0
total <- total + 72
total <- total + 85
total <- total + 90
let mutable average = 0.0
average <- float total / 3.0

The variables total and average start with placeholder values and are changed with <- (“assign”). To know what average holds, you have to replay the steps in order in your head. If one step is moved or forgotten, the answer silently changes.

Here is the same computation, written the way we will write most F#:

// Expression style: say what the average IS.
let averageOf3 a b c = float (a + b + c) / 3.0
let myAverage = averageOf3 72 85 90

There is nothing to replay. averageOf3 a b c is float (a + b + c) / 3.0, always, and myAverage is averageOf3 72 85 90. Each name is defined once and never changes.

This difference is the heart of the course:

Imperative style Functional style
A program is… a sequence of statements that change state a set of expressions and functions that define values
A variable is… a box whose contents change over time a name for a value that never changes
To understand it you… replay the steps in order replace names by what they mean

F# supports both styles. We will learn to prefer the second, and to use the first deliberately, when there is a reason.

4 Values, bindings, and environments

4.1 let binds a name to a value

let price = 25 * 5
let newPrice = 2 * price
let isExpensive = newPrice > 500

In FSI:

> let price = 25 * 5;;
val price: int = 125

> let newPrice = 2 * price;;
val newPrice: int = 250

> let isExpensive = newPrice > 500;;
val isExpensive: bool = false

let price = 25 * 5 does two things: it evaluates the expression 25 * 5 to the value 125, and it binds the name price to that value. We write the binding as

price ↦ 125

and read it as “price is bound to 125”. The collection of all bindings currently in effect is called the environment. After the three declarations above, the environment contains:

[ price ↦ 125,   newPrice ↦ 250,   isExpensive ↦ false ]

When F# evaluates 2 * price, it looks price up in the environment and finds 125.

Notice that we never wrote a type. F# worked out that price is an int because 25 * 5 is an int. This is called type inference. The types are still there, and they are checked strictly; you just don’t have to write most of them. Week 2 looks at type inference more closely.

4.2 A binding does not change

In FSI you are allowed to type let with a name that already exists:

> let rate = 7;;
val rate: int = 7

> let addTax amount = amount + amount * rate / 100;;
val addTax: amount: int -> int

> let rate = 10;;
val rate: int = 10

> addTax 100;;
val it: int = 107

If let rate = 10 had changed rate, then addTax 100 would give 110. It gives 107. The second let created a new binding that happens to use the same name. From then on, the name rate refers to the new binding, but addTax was defined earlier and still refers to the old one. This is called shadowing: the new binding hides the old one; it does not modify it.

The same thing happens inside a function or a block, where re-using a name is also allowed:

let taxDemo =
    let rate = 7
    let addTax amount = amount + amount * rate / 100   // uses rate = 7
    let rate = 10                                      // a NEW binding named rate
    addTax 100                                         // still 107, not 110
WarningFSI vs script files

Re-using a top-level name works in an FSI session because each thing you type is treated as a separate step. In a script file, two top-level let rate = … lines are an error (Duplicate definition of value 'rate'). Shadowing is still allowed inside functions and blocks. In practice, avoid re-using names at the top level anyway; it makes code harder to read.

5 Everything is an expression

In C, Java, or Python, if is a statement: it chooses which instructions to run, and produces nothing. In F#, if … then … else is an expression: it produces a value.

let temperature = 34
let advice =
    if temperature > 30 then "Stay hydrated"
    else "Enjoy the weather"

advice is bound to "Stay hydrated". The if works like a function of the condition that returns one of two values. You can chain conditions with elif (“else if”):

let describe t =
    if t > 35 then "very hot"
    elif t > 30 then "hot"
    elif t > 20 then "pleasant"
    else "cool"

Because an if expression must produce a value, two rules follow.

Both branches must have the same type. Otherwise F# cannot say what type the whole expression has:

> if 2 > 1 then 10 else "twenty";;

  if 2 > 1 then 10 else "twenty";;
  ----------------------^^^^^^^^

error FS0001: All branches of an 'if' expression must return values implicitly
convertible to the type of the first branch, which here is 'int'. This branch
returns a value of type 'string'.

There must be an else if the then branch produces a real value. What would if false then "yes" be?

> if 3 > 2 then "yes";;

  if 3 > 2 then "yes";;
  --------------^^^^^

error FS0001: This 'if' expression is missing an 'else' branch. Because 'if' is
an expression, and not a statement, add an 'else' branch which also returns a
value of type 'string'.

The compiler says it directly: if is an expression, and not a statement.

5.1 Blocks: the last expression is the result

A function body can span several lines. Lines that start with let introduce local bindings, visible only in the lines below them. The last line is an expression, and its value is the result of the whole block:

let totalWithVat price quantity =
    let subtotal = price * quantity   // local binding
    let vat = subtotal * 7 / 100      // Thai VAT: 7%
    subtotal + vat                    // the result

There is no return keyword. The body of totalWithVat is an expression, and subtotal + vat is its final part.

ImportantIndentation matters

F# uses indentation to decide what belongs to what. Everything in the body of totalWithVat must be indented more than let totalWithVat, and the lines of the body must line up with each other. Use spaces, not tabs (your editor will do this for you).

5.2 But what about printfn?

Here is a fair question. If everything is an expression that produces a value, what is printfn "Hello"? It clearly does something: it prints.

The answer is that printfn "Hello" is an expression, and evaluating it has two results:

  • it produces a value: (), pronounced “unit”, the only value of the type unit;
  • while it is being evaluated, it prints. Something happens in the world beyond producing the value. That is called a side effect.
let greet name =
    printfn "Hello, %s!" name    // printfn returns () : unit

let greeting = greet "Somchai"   // greeting : unit = ()
> let greet name = printfn "Hello, %s!" name;;
val greet: name: string -> unit

So two different properties are easy to mix up:

Property What it means Does F# guarantee it?
Everything is an expression Every construct produces a value with a type, even if the value is just (). There are no statements. Yes. It is how the language is built.
Pure Evaluating the expression does nothing except produce its value: no printing, no changing variables, no reading input or files. No. 2 + 3 is pure; printfn "Hello" is not. Keeping code pure is our discipline.

This course is largely about the second property: writing as much of a program as possible out of pure expressions, and keeping the side effects few, visible, and at the edges.

5.2.1 Effects happen when an expression is evaluated

A side effect happens at the moment its expression is evaluated, and only then:

let u = printfn "computing..."   // prints now, once
let v = u                        // u is just (), nothing is printed
> let u = printfn "computing...";;
computing...
val u: unit = ()

> u;;
val it: unit = ()

The message is printed once, when u is bound. After that, u is just the value (), and using it prints nothing. The value was kept; the effect was not.

5.2.2 Blocks run their effects in order

This also explains how blocks work when they contain effects. The lines before the last are evaluated in order, top to bottom, only for their effects, and their values are thrown away. The last line gives the block its value:

let answer () =
    printfn "thinking..."        // evaluated first, for its effect
    printfn "almost there..."    // then this one
    42                           // the value of the whole block
> answer ();;
thinking...
almost there...
val it: int = 42

Since the values of the earlier lines are thrown away, they should be (). If one of them produces a real value, F# warns you, because a discarded value is usually a mistake:

> let bad () =
      42
      printfn "done";;

warning FS0020: The result of this expression has type 'int' and is implicitly
ignored. Consider using 'ignore' to discard this value explicitly, ...
val bad: unit -> unit

If you really do want to throw a value away, say so by passing it to ignore:

let logAndReturn x =
    printfn "value = %d" x
    x

logAndReturn 5 |> ignore         // we only wanted the printing

The |> symbol means “pass the value on the left into the function on the right”; we will use it a lot from Week 5.

5.2.3 unit in a type is a warning sign

Look again at greet: name: string -> unit. The type says: “give me a string, and I will give you back nothing interesting”. A function like that can only be useful because of what it does, never because of what it returns. So whenever you see -> unit at the end of a type, expect a side effect. (F# cannot stop you from hiding an effect inside a function that returns something else, like nextId below. The unit hint is only a hint.)

TipA small preview of Week 2

Try let say = printfn "Hello, %s!";; in FSI. Without the name argument, printfn "Hello, %s!" is already a function of type string -> unit, waiting for its string. F# even checks that the %s matches the argument you give it. Week 2 explains how this works.

6 A few basic types

Type Example values Notes
int 0, 42, -7 whole numbers (32-bit)
float 3.14, 2.0, -0.5 floating point; a float literal always has a .
bool true, false result of comparisons =, <>, <, <=, …
string "hello", "" text; join with +
char 'a', 'ก' a single character, single quotes
unit () the only value of type unit 
let count = 42                 // int
let ratio = 0.75               // float
let name = "Nattapong"         // string
let initial = 'N'              // char
let passed = count > 40        // bool
let nothing = ()               // unit

A few operators behave in ways that may surprise you:

> 7 / 2;;
val it: int = 3

> 7.0 / 2.0;;
val it: float = 3.5

> 7 % 2;;
val it: int = 1

> "7" + "2";;
val it: string = "72"

Integer division throws away the remainder, % gives the remainder, and + on strings joins them. Equality is a single = (not ==), and “not equal” is <>.

6.1 Arithmetic never mixes int and float

> 2 * 3.0;;

  2 * 3.0;;
  ----^^^

error FS0001: The type 'float' does not match the type 'int'

Many languages quietly convert 2 to 2.0 here. F# refuses, because silent conversions are a classic source of bugs. You convert explicitly, using the type name as a function:

let items = 3
let unitPrice = 19.5
let cost = float items * unitPrice   // float 3 is 3.0
let rounded = int 57.9               // truncates: 57

Similarly, int "42" turns a string into an int, and string 42 turns a number into a string.

NoteOne exception you will meet

Since F# 6, when the compiler already knows that a float is expected, for example when you pass an argument to a function whose parameter is a float, it will widen an int for you. So circleArea 2 works even though circleArea expects a float. Arithmetic operators still never mix the two: 2 * 3.0 and n + 1.5 (with n : int) are errors. When in doubt, write the conversion.

6.2 Building strings

Put $ in front of a string to interpolate expressions inside {…}:

let student = "Ploy"
let score = 87
let report = $"{student} scored {score} points, {100 - score} short of full marks"

report is "Ploy scored 87 points, 13 short of full marks". Anything inside the braces is an ordinary F# expression.

7 Functions

7.1 Defining and applying functions

let circleArea r = System.Math.PI * r * r
let area1 = circleArea 1.0
let area2 = circleArea 2.5
> let circleArea r = System.Math.PI * r * r;;
val circleArea: r: float -> float

let circleArea r = … declares a function named circleArea with one parameter r. FSI reports its type as r: float -> float: a function from float to float. F# inferred that r is a float because it is multiplied by System.Math.PI, which is a float.

To apply a function, write the function followed by its argument, separated by a space. No parentheses are needed:

circleArea 2.5

Parentheses are only for grouping. Function application binds more tightly than any operator, so:

let square x = x * x

let a1 = square 3 + 1        // (square 3) + 1 = 10
let a2 = square (3 + 1)      // square 4       = 16

square 3 + 1 means (square 3) + 1. If you want to square 3 + 1, you must say so with parentheses.

NoteWhen F# can’t tell which kind of number you mean

FSI reports square as x: int -> int. Nothing in x * x says whether x is an int or a float, and in that case F# assumes int. Compare circleArea, where System.Math.PI settles the question. Week 2 shows how to state the type yourself when you want something else.

7.2 Functions with two parameters

A function can take several parameters, separated by spaces, and is applied the same way:

let totalCost unitPrice quantity = unitPrice * float quantity
let order = totalCost 19.5 4
> let totalCost unitPrice quantity = unitPrice * float quantity;;
val totalCost: unitPrice: float -> quantity: int -> float

The type float -> int -> float reads “takes a float, then an int, and produces a float”. F# worked out that quantity is an int because it is converted with float, and that unitPrice is a float because it is multiplied by a float. The repeated arrows are not an accident; in Week 2 we will see what they really mean, and why they are so useful. For now, read the last type as the result and everything before it as the parameters.

WarningDon’t write f(a, b)

In C or Java you would call totalCost(19.5, 4). In F#, (19.5, 4) is a single value, a pair (Week 3), so totalCost (19.5, 4) passes one argument and gives a type error (expected to have type 'float' but here has type 'float * int'). Write totalCost 19.5 4.

7.3 Anonymous functions

A function does not need a name. fun x -> 2 * x is a function value, just as 42 is an integer value:

let double = fun x -> 2 * x     // same as: let double x = 2 * x
let eight = (fun x -> 2 * x) 4  // apply it directly
> fun s -> String.length s;;
val it: s: string -> int

let double x = 2 * x is simply a shorter way of writing let double = fun x -> 2 * x. A function is a value like any other: it can be bound to a name, passed to another function, or returned from one. Anonymous functions (also called lambdas) become essential from Week 5.

8 Evaluation by substitution

Here is the most important idea of this week. Because names never change, we can work out what a program computes by hand, by repeatedly replacing things with what they mean. You already do this in algebra.

8.1 The rules

To evaluate an expression, repeat until you reach a value:

  1. Replace a name by the value it is bound to.
  2. Evaluate the arguments of a function application to values first.
  3. Apply a function by taking its body and replacing each parameter with the matching argument value.
  4. Evaluate an operator (+, *, >, …) once both sides are values.
  5. Evaluate an if by evaluating the condition, then keep only the chosen branch.
  6. Evaluate a local let x = e in a block by evaluating e to a value v, then replacing x by v in the lines below it.

We write ⇝ for “evaluates in one step to”.

8.2 A first trace

With these definitions:

let square x = x * x

let a1 = square 3 + 1        // (square 3) + 1 = 10
let a2 = square (3 + 1)      // square 4       = 16
let sumOfSquares a b = square a + square b

let’s evaluate sumOfSquares 3 (1 + 1):

   sumOfSquares 3 (1 + 1)
⇝ sumOfSquares 3 2              (2) evaluate the arguments
⇝ square 3 + square 2           (3) body of sumOfSquares, a ↦ 3, b ↦ 2
⇝ (3 * 3) + square 2            (3) body of square, x ↦ 3
⇝ 9 + square 2                  (4)
⇝ 9 + (2 * 2)                   (3) body of square, x ↦ 2
⇝ 9 + 4                         (4)
⇝ 13                            (4)

Every line is an ordinary F# expression, and every line has the same value, 13. Evaluation is just rewriting an expression into simpler expressions with the same meaning, until nothing is left to simplify.

8.3 A trace with if

A courier charges by weight (in kg):

let shippingFee weight =
    if weight <= 1 then 40
    elif weight <= 5 then 40 + (weight - 1) * 15
    else 100 + (weight - 5) * 10
   shippingFee 3
⇝ if 3 <= 1 then 40                               (3) weight ↦ 3
   elif 3 <= 5 then 40 + (3 - 1) * 15
   else 100 + (3 - 5) * 10
⇝ if false then 40 elif 3 <= 5 then …             (4)
⇝ if 3 <= 5 then 40 + (3 - 1) * 15 else …         (5) drop the first branch
⇝ if true then 40 + (3 - 1) * 15 else …           (4)
⇝ 40 + (3 - 1) * 15                               (5) keep the chosen branch
⇝ 40 + 2 * 15                                     (4)
⇝ 40 + 30                                         (4)
⇝ 70                                              (4)

Notice that the branches that were not chosen are never evaluated. Only the condition decides.

8.4 A trace with local bindings

Recall totalWithVat from earlier:

let totalWithVat price quantity =
    let subtotal = price * quantity   // local binding
    let vat = subtotal * 7 / 100      // Thai VAT: 7%
    subtotal + vat                    // the result
   totalWithVat 250 4
⇝ let subtotal = 250 * 4                  (3) price ↦ 250, quantity ↦ 4
   let vat = subtotal * 7 / 100
   subtotal + vat
⇝ let vat = 1000 * 7 / 100                (6) subtotal ↦ 1000
   1000 + vat
⇝ 1000 + 70                               (6) vat ↦ 70
⇝ 1070                                    (4)

(We skipped writing 250 * 4 ⇝ 1000 and 1000 * 7 / 100 ⇝ 70 as separate steps. Once you are comfortable, you may combine obvious arithmetic steps.)

TipTraces are a debugging tool

You will not write traces for every function you ever write. But when a function gives a result you don’t expect, tracing a small input by hand is often the fastest way to find out why. Many of this week’s drills are traces, so that the habit becomes automatic.

8.5 The substitution rule, stated plainly

What makes this work is a simple property:

Anywhere a name appears, you can replace it by its definition, and anywhere an expression appears, you can replace it by its value, without changing what the program means.

This property has a name: referential transparency. It is what lets you reason about each piece of a functional program separately, the way you simplify one part of an algebraic equation without worrying about the rest.

8.6 When substitution breaks

Now consider a function that changes a mutable variable:

let mutable counter = 0
let nextId () =
    counter <- counter + 1
    counter

let x1 = nextId () + nextId ()   // 1 + 2 = 3
let x2 = 2 * nextId ()           // 2 * 3 = 6

In mathematics, f(x) + f(x) = 2\,f(x) holds for every function f and every x. Here, with x being (), nextId () + nextId () is 3, but 2 * nextId () is 6. The expression nextId () does not have one fixed value: it depends on when it is evaluated, and evaluating it changes the world for everyone else. You can no longer replace nextId () by “its value”, because it has none. To understand this code, you are back to replaying steps in order.

Mutation is not the only culprit. Any side effect breaks substitution in the same way:

  • printfn "Hi" has the value (), but replacing it by () changes the program: the output disappears.

  • Reading the clock gives a different value each time. After the lines below, t1 and t2 may differ, even though they come from the same expression:

    let t1 = System.DateTime.Now
let t2 = System.DateTime.Now     // same expression, possibly a different value

  • The same holds for reading input, files, or the network, and for random numbers.

This is the real reason functional programmers avoid mutation and keep other side effects at the edges of a program. It isn’t a matter of style. Wherever there are side effects, the simple reasoning of this section stops working, and you are back to replaying steps in order.

9 Immutability

F# values are immutable by default: once a value exists, it never changes. “Changing” something always means computing a new value.

let salary = 30000.0
let raised = salary * 1.05         // a new value; salary is still 30000.0

Strings behave the same way. Methods that seem to modify a string actually return a new one:

let original = "functional"
let shouted = original.ToUpper()   // a new string; original is unchanged

9.1 Why it matters: sharing is safe

Arrays are one of the few mutable things in F#. Look at what happens when two names refer to the same array:

let scores = [| 70; 80; 90 |]   // an array: mutable
let backup = scores             // NOT a copy!
scores[0] <- 0
let surprise = backup[0]        // 0: backup changed too

backup was supposed to be a safety copy, but let backup = scores only gives the same array a second name. Changing it through one name changes it for the other. This kind of bug, called aliasing, is common in every imperative language, and gets much worse in large programs and in programs that run several things at once (Week 12).

With immutable values, aliasing is harmless. If nobody can change a value, it does not matter how many names refer to it. You can pass it to any function, store it anywhere, share it between threads, and it stays what it was.

9.2 Mutation is available, but explicit

F# does allow mutable variables, with let mutable and the assignment operator <-, as in the counter example. It is a tool for special situations, such as a tight loop where performance matters, or code that talks to libraries written in an imperative style. In this course, use it only when you can say why.

Warning= is not assignment

In F#, = compares. <- assigns.

> let mutable x = 1;;
val mutable x: int = 1

> x = 2;;
val it: bool = false

x = 2 does not change x; it asks “is x equal to 2?” and answers false. If you meant to assign, write x <- 2.

10 Beyond F#

The two big ideas of this week, write computations as expressions and prefer bindings that don’t change, can be applied in almost any modern language, though with different amounts of help from the language.

Language Conditional as an expression Binding that can’t be reassigned Watch out for
Rust let a = if t > 30 { "hot" } else { "ok" }; Blocks are expressions, as in F#. let (use let mut to allow change) Closest to F# on both points.
Kotlin val a = if (t > 30) "hot" else "ok"; also when val (vs var) val fixes the name, not the object it refers to.
TypeScript / JavaScript const a = t > 30 ? "hot" : "ok"; const const scores = [1, 2]; scores[0] = 9; is allowed: const does not make the array immutable.
C# var a = t > 30 ? "hot" : "ok";; switch expressions readonly fields; records with with Local variables can always be reassigned; only compile-time const values are fixed.
Java var a = t > 30 ? "hot" : "ok";; switch expressions (Java 14+) final final fixes the reference only; records are shallowly immutable.
Python a = "hot" if t > 30 else "ok" none (only convention) Use tuples, frozenset, and frozen dataclasses for values that shouldn’t change.

A habit you can carry anywhere: declare with the non-reassignable form by default (const, val, final, let), write conditionals that produce a value instead of assigning to a variable in each branch, and treat “update” as “compute a new value”. Your code will be easier to test and reason about, in any language.

11 Going further (optional)

NoteFunctions as mathematics: the λ-calculus

In the 1930s, Alonzo Church described computation using only functions, in a system called the λ-calculus (lambda calculus). The function x \mapsto x + 2 is written \lambda x.\, x + 2, which is exactly F#’s fun x -> x + 2. Applying a function,

(\lambda x.\, x \times x)\ 7 \;\longrightarrow_{\beta}\; 7 \times 7,

is called β-reduction, and it is precisely rule (3) of our substitution model. Remarkably, the λ-calculus can express any computation a computer can perform, even though it has nothing but functions. Functional languages from LISP (1958) through ML (1970s), OCaml, Haskell, and F# are all built on this foundation. This is also where the word “lambda” in Python’s lambda and in “lambda expressions” in Java and C# comes from.

NoteEvaluation order

Our rule (2) says: evaluate the arguments before applying the function. This is called strict (or call-by-value) evaluation, and it is what F#, OCaml, Rust, Java, Python, and most languages do. Some languages, notably Haskell, are lazy: they substitute the unevaluated argument into the body and only evaluate it if it’s actually needed. A remarkable result about pure programs (the Church–Rosser property) says that if both orders finish, they give the same answer. The order only matters for efficiency, for whether the computation finishes at all, and, of course, when there are side effects.

Even strict languages make a few exceptions. if only evaluates the chosen branch, and && and || stop as soon as the answer is known:

> let zero = 0;;
val zero: int = 0

> false && (10 / zero = 1);;
val it: bool = false

The division by zero is never evaluated. We will meet laziness on purpose in Week 7.

NoteLanguages that make effects visible in the type

F# trusts you to keep effects under control; the unit result type is only a hint. Haskell goes further: a function that performs input or output must say so in its type. A function that prints has type IO () rather than (), and a pure function simply cannot call it. The type checker then guarantees which parts of a program are pure. IO is one example of a monad, a word you will often hear around functional programming. It is much less scary than its reputation, and we will meet it properly, by name, in Week 8. Newer languages and libraries explore similar ideas under the name effect systems. F# chooses convenience instead, and in Week 10 we will see a design pattern, functional core, imperative shell, that gets much of the benefit through discipline rather than enforcement.

12 Summary

  • A functional program is built from expressions that denote values and functions that map values to values.
  • let binds a name to a value. The set of bindings is the environment. A binding never changes; let with an existing name makes a new binding (shadowing).
  • In F#, if … then … else is an expression: both branches need the same type, and the else is required. A block’s value is its last expression.
  • Everything is an expression, but not every expression is pure. printfn produces () and has a side effect. Effects happen when an expression is evaluated, once, in order; -> unit in a type signals one.
  • F# never mixes int and float in arithmetic. Convert with float, int, string.
  • Apply functions by juxtaposition: f x y, not f(x, y). Parentheses only group.
  • Without mutation, you can evaluate a program by substitution: replace names by their definitions and expressions by their values (referential transparency). Side effects, such as mutation, printing, and reading the clock, break this.
  • Values are immutable by default; “changing” means computing a new value. Immutable values can be shared safely.
