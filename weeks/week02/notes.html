Week 2 · Functions, Recursion, and Reading Types

Lecture notes

NoteAfter this week you should be able to
  • write recursive functions using a four-step recipe, and trace them by hand;
  • write case analysis with match, and read a match as a set of equations;
  • recognise the common ways recursion goes wrong, and fix them;
  • read a function type with several arrows, and use partial application;
  • work out the type of a function by hand, including generic types like 'a -> 'a;
  • add a type annotation where F# needs one.

This week is about practice more than new ideas. Recursion is the main way functional programs repeat things, and the aim is for writing recursive functions to become second nature. That only comes from writing many of them. So these notes contain many small worked examples, all following the same recipe, and the drills and lab contain many more. Do as many as you can.

1 Functions that call themselves

1.1 A definition in terms of itself

The factorial of a natural number n is the product 1 \times 2 \times \cdots \times n, written n!. The “\cdots” is fine on paper, but a program needs something more precise. Notice that

5! = 5 \times \underbrace{4 \times 3 \times 2 \times 1}_{4!} = 5 \times 4!

In general, n! = n \times (n-1)!. The factorial of n is defined in terms of the factorial of a smaller number. Together with a starting point, this gives a complete definition:

n! = \begin{cases} 1 & \text{if } n = 0 \\ n \times (n-1)! & \text{if } n > 0 \end{cases}

(By convention 0! = 1, the empty product.) This translates directly into F#:

let rec factIf n =
    if n = 0 then 1
    else n * factIf (n - 1)

A function that calls itself is recursive. In F# you must say so with the keyword rec. Without it, the name factIf isn’t bound yet inside its own body:

> let fact n = if n = 0 then 1 else n * fact (n - 1);;

  let fact n = if n = 0 then 1 else n * fact (n - 1);;
  --------------------------------------^^^^

error FS0039: The value or constructor 'fact' is not defined.

1.2 Tracing a recursive function

Recursion needs no new evaluation rules. The substitution rules from Week 1 already cover it:

   factIf 3
⇝ if 3 = 0 then 1 else 3 * factIf (3 - 1)                 (3)
⇝ 3 * factIf (3 - 1)                                      (4),(5)
⇝ 3 * factIf 2                                            (4)
⇝ 3 * (if 2 = 0 then 1 else 2 * factIf (2 - 1))           (3)
⇝ 3 * (2 * factIf 1)                                      (4),(5),(4)
⇝ 3 * (2 * (1 * factIf 0))                                same steps again
⇝ 3 * (2 * (1 * (if 0 = 0 then 1 else 0 * factIf (0 - 1))))   (3)
⇝ 3 * (2 * (1 * 1))                                       (4),(5)
⇝ 3 * (2 * 1)
⇝ 3 * 2
⇝ 6

Look at the shape of this trace. The expression first grows, as each call leaves a multiplication waiting for the result of the next call. When the base case is reached, it shrinks again, as the waiting multiplications are done from the inside out. The computer has to remember that waiting work somewhere; it uses a region of memory called the call stack. Week 7 looks at what that costs, and how to avoid it.

1.3 The shortcut: tracing with equations

Full traces are useful when you are unsure. Once you are comfortable, you can skip the if steps and write only the equations:

factIf 3 = 3 * factIf 2
         = 3 * (2 * factIf 1)
         = 3 * (2 * (1 * factIf 0))
         = 3 * (2 * (1 * 1))
         = 6

This is how most functional programmers check a recursive function in their head. Each line is still a valid substitution, and each line has the same value.

2 A recipe for recursive functions

Every recursive function in this course can be written with the same four steps. Do them in this order, every time, until you do them without thinking.

  1. Type — Say what goes in and what comes out. Writing it down is half of understanding the problem.
  2. Base case — Find the input that is so small the answer is obvious, and write that answer.
  3. Recursive case — For a bigger input, assume the function already works for a smaller input, and build the answer from that smaller answer.
  4. Check — Trace a small input. Then ask: does every recursive call get closer to the base case?

Step 3 is where most people get stuck, because it feels like cheating. How can you use a function you are still writing? The trick is not to think about how the smaller call works; trust it, the way you trust sqrt without knowing its code. Your only job is: if the smaller call gives the right answer, does your formula give the right answer for the bigger input? Step 4 then checks that the trust is justified.

2.1 The recipe in action: sumTo

Problem: add up all the numbers from 1 to n.

  1. Type — A number in, a number out: int -> int.
  2. Base case — The sum of no numbers is 0, so sumTo 0 = 0.
  3. Recursive case — Suppose sumTo (n - 1) correctly gives 1 + 2 + \cdots + (n-1). Then adding n gives the answer for n: sumTo n = n + sumTo (n - 1).
  4. Check — sumTo 3 = 3 + sumTo 2 = 3 + (2 + sumTo 1) = 3 + (2 + (1 + sumTo 0)) = 3 + (2 + (1 + 0)) = 6. Each call subtracts 1, so any n ≥ 0 eventually reaches 0.
let rec sumToIf n =
    if n = 0 then 0
    else n + sumToIf (n - 1)

3 Another way to write it: match

Look again at the math definition of factorial. It is a list of cases: one equation for 0, one for everything else. F# has a construct that lets us write exactly that, match:

\begin{aligned} 0! &= 1 \\ n! &= n \times (n-1)! \end{aligned} 

let rec fact n =
    match n with
    | 0 -> 1
    | n -> n * fact (n - 1)

Read match n with as “look at n, and consider these cases”. Each line starting with | is a rule of the form pattern -> expression:

  • The rule | 0 -> 1 says: if n is 0, the result is 1.
  • The rule | n -> n * fact (n - 1) says: otherwise, call the value n, and the result is n * fact (n - 1).

The F# code is the math definition, with slightly different punctuation. This is one of the things that makes functional languages pleasant: a definition you would write on paper can often be typed in almost as it is.

3.1 How a match is evaluated

We add one rule to the substitution model from Week 1:

  1. Evaluate a match by first evaluating the value being matched. Then try the patterns from top to bottom. For the first pattern that fits, bind the names in the pattern, and continue with that rule’s expression.
   fact 3
⇝ match 3 with | 0 -> 1 | n -> n * fact (n - 1)       (3)
⇝ 3 * fact (3 - 1)                                    (7) 3 isn't 0; n ↦ 3
⇝ 3 * fact 2                                          (4)
⇝ 3 * (2 * fact 1)                                    (3),(7),(4)
⇝ 3 * (2 * (1 * fact 0))                              (3),(7),(4)
⇝ 3 * (2 * (1 * 1))                                   (3),(7) 0 fits the first rule
⇝ 6                                                   (4)

A match is an expression, just like if, so the same rule applies: every rule must produce a value of the same type.

3.2 Kinds of patterns

This week we use four kinds of patterns. Week 4 adds many more.

Pattern Example Matches Binds a name?
Constant 0, "Sunday", true only that value no
Name n, x, day any value yes: the name is bound to the value
Wildcard _ any value no (“I don’t care what it is”)
Or "Saturday" | "Sunday" either alternative only if both sides bind the same names 
let isWeekend day =
    match day with
    | "Saturday" -> true
    | "Sunday" -> true
    | _ -> false            // _ matches anything

With an or-pattern, the first two rules can be combined:

let isWeekend' day =
    match day with
    | "Saturday" | "Sunday" -> true
    | _ -> false

3.3 Guards: conditions on a rule

Sometimes a case isn’t a single value but a range: “all positive numbers”. Add a guard with when:

let sign n =
    match n with
    | 0 -> 0
    | n when n > 0 -> 1     // guard: only if n > 0
    | _ -> -1

The rule | n when n > 0 -> 1 applies only if the pattern fits and the condition is true. If the guard is false, F# moves on to the next rule.

NoteWhy does the pattern n reuse the parameter’s name?

In fact, the parameter is n, and the second rule’s pattern is also n. The pattern makes a new binding, to the same value, which shadows the old one (Week 1). That’s harmless here, and it keeps the code close to the math. You could just as well write | k -> k * fact (k - 1), or | _ -> n * fact (n - 1), which uses the parameter itself.

3.4 The compiler checks your cases

Because a match is a list of cases, F# can check the list for you. If some value is not covered, you get a warning with an example:

> let describe n =
      match n with
      | 0 -> "zero"
      | 1 -> "one";;

warning FS0025: Incomplete pattern matches on this expression. For example, the
value '2' may indicate a case not covered by the pattern(s).

If a rule can never be reached because an earlier rule already catches everything, you get a different warning:

> let rec bad n =
      match n with
      | n -> n * bad (n - 1)
      | 0 -> 1;;

      | 0 -> 1;;
  ------^

warning FS0026: This rule will never be matched

Take both warnings seriously. The second one describes a real bug: bad never reaches its base case, and runs until the program crashes (see below). This checking becomes much more powerful in Week 4, when we define our own types.

3.5 if or match?

Both are expressions and both work. As a rule of thumb:

  • use if for a single yes-or-no condition, such as if balance < 0 then … else …;
  • use match when you are distinguishing cases of a value, which is what almost every recursive function does.

For the rest of this course, recursive functions are written with match.

TipThe function shorthand

Matching on the last parameter is so common that F# has a shorthand. function means “a function whose argument is matched immediately”:

let rec factF =
    function
    | 0 -> 1
    | n -> n * factF (n - 1)

This is the same as fact. You will see this style in other people’s F# code. In FSI the argument appears with the made-up name _arg1 (val factF: _arg1: int -> int), because we never named it.

4 The recursion ladder

Each example below adds one new wrinkle. Work through them with the recipe in mind: for each one, cover the code, write down the four steps yourself, and only then compare.

4.1 Two parameters: power

Problem: compute x^n for a float x and a natural number n.

\begin{aligned} x^0 &= 1 \\ x^n &= x \times x^{n-1} \end{aligned} 

let rec power x n =
    match n with
    | 0 -> 1.0
    | n -> x * power x (n - 1)
  1. Type — float -> int -> float. The base case 1.0 decides that the result is a float, and x * … makes x a float too.
  2. Base case — power x 0 = 1.0.
  3. Recursive case — trust power x (n - 1), and multiply by one more x.
  4. Check — power 2.0 3 = 2.0 * (2.0 * (2.0 * 1.0)) = 8.0. Only n gets smaller; x is passed along unchanged.

4.2 Building text: repeat

Problem: repeat "ab" 3 should give "ababab".

let rec repeat s n =
    match n with
    | 0 -> ""
    | n -> s + repeat s (n - 1)
  1. Type — string -> int -> string.
  2. Base case — repeating a string zero times gives the empty string "".
  3. Recursive case — one copy of s, followed by n - 1 copies.
  4. Check — repeat "ab" 2 = "ab" + ("ab" + "") = "abab".

Recursion isn’t only for arithmetic. Any result you can build piece by piece can be built recursively.

4.3 Two base cases: binary

Problem: write a natural number in base 2, as a string: binary 6 = "110".

The last binary digit of n is n % 2, and the digits before it are the binary digits of n / 2. For example, 6 = 2 \times 3 + 0, so binary 6 is binary 3 followed by "0".

let rec binary n =
    match n with
    | 0 -> "0"
    | 1 -> "1"
    | n -> binary (n / 2) + string (n % 2)
  1. Type — int -> string.
  2. Base cases — 0 and 1 are their own binary digits. We need both: if only 0 were a base case, binary 1 would give binary 0 + "1" = "01".
  3. Recursive case — the digits of n / 2, then the last digit.
  4. Check — binary 6 = binary 3 + "0" = (binary 1 + "1") + "0" = "1" + "1" + "0" = "110". Here the input gets smaller by halving, not by subtracting 1. That’s fine: halving a positive number repeatedly always reaches 1.

4.4 “Smaller” isn’t always n - 1: digitSum

Problem: add up the decimal digits of a number: digitSum 1234 = 1 + 2 + 3 + 4 = 10.

let rec digitSum n =
    match n with
    | n when n < 10 -> n
    | n -> n % 10 + digitSum (n / 10)
  1. Type — int -> int.
  2. Base case — a number below 10 has one digit, which is its own digit sum. The base case is a range, so it uses a guard.
  3. Recursive case — the last digit is n % 10; the other digits form the number n / 10.
  4. Check — digitSum 1234 = 4 + digitSum 123 = 4 + (3 + digitSum 12) = 4 + (3 + (2 + 1)) = 10. Each call removes one digit.

4.5 No waiting work: gcd

Problem: the greatest common divisor of two natural numbers. Euclid’s method (from around 300 BC) is based on a neat fact: the GCD of a and b is the same as the GCD of b and the remainder a \bmod b.

\begin{aligned} \gcd(a, 0) &= a \\ \gcd(a, b) &= \gcd(b,\ a \bmod b) \end{aligned} 

let rec gcd a b =
    match b with
    | 0 -> a
    | b -> gcd b (a % b)
gcd 48 18 = gcd 18 12      48 % 18 = 12
          = gcd 12 6       18 % 12 = 6
          = gcd 6 0        12 % 6  = 0
          = 6

Compare this trace with fact’s. Here, nothing is left waiting: each call’s answer is the next call’s answer, so the expression never grows. Keep that difference in mind. It becomes important in Week 7.

Check: why does gcd stop? The second argument always gets smaller, because a remainder a % b is always less than b. A natural number can’t get smaller forever, so it must reach 0.

4.6 Two recursive calls: fib

Problem: the Fibonacci numbers 0, 1, 1, 2, 3, 5, 8, 13, …, where each is the sum of the two before it.

let rec fib n =
    match n with
    | 0 -> 0
    | 1 -> 1
    | n -> fib (n - 1) + fib (n - 2)

This is correct, and it reads exactly like the definition. But try it in FSI with timing switched on (#time "on";;):

> fib 40;;
Real: 00:00:01.002, CPU: 00:00:00.980, GC gen0: 0, gen1: 0, gen2: 0
val it: int = 102334155

> fib 42;;
Real: 00:00:02.254, CPU: 00:00:02.226, GC gen0: 0, gen1: 0, gen2: 0
val it: int = 267914296

Each extra step makes it about 1.6 times slower, so fib 50 would take minutes. The reason becomes clear if you draw the calls: fib 5 calls fib 4 and fib 3; fib 4 calls fib 3 again, and so on. The same values are computed over and over. A function can be correct and still be a bad program. In Week 7 we will write a version that takes microseconds.

5 When recursion goes wrong

5.1 No way to reach the base case

What does fact (-1) do? The only base case is 0, and -1, -2, -3, … never reach it. Each call waits for the next one, and the call stack fills up until the program crashes:

Stack overflow.
Repeated 261720 times:
--------------------------------
   at FSI_0001.fact(Int32)
--------------------------------

The same thing happens if the recursive call doesn’t make the input smaller, for example n * fact n instead of n * fact (n - 1), or if the base case comes after a rule that catches everything (the FS0026 warning above).

When a function is only meant for some inputs, say so explicitly. failwith stops the program with a message:

let rec factSafe n =
    match n with
    | n when n < 0 -> failwith "factSafe: negative input"
    | 0 -> 1
    | n -> n * factSafe (n - 1)

A clear error is better than a crash deep inside the recursion. (Stopping the program is still a blunt tool. Week 4 shows how a function can return “no answer” instead.)

5.2 Numbers that are too big

> fact 12;;
val it: int = 479001600

> fact 13;;
val it: int = 1932053504

The real value of 13! is 6,227,020,800. An int holds only values up to about 2.1 billion (2^{31} - 1), and arithmetic that goes past that wraps around silently. fact 20 even comes out negative. For bigger numbers, use int64 (64-bit integers), whose literals end in L:

let rec factBig (n: int64) : int64 =
    match n with
    | 0L -> 1L
    | n -> n * factBig (n - 1L)

factBig 20L is 2432902008176640000L. (For unlimited size there is also bigint, with literals like 20I.)

6 Reading types

6.1 Many arrows: currying

In Week 1 we saw that a function with two parameters has a type with two arrows:

> let add x y = x + y;;
val add: x: int -> y: int -> int

Arrows group to the right, so int -> int -> int means int -> (int -> int). Read literally: add takes an int and returns a function that takes another int and returns an int. And that is exactly how F# treats it. Give add just one argument, and you get that function back:

let add x y = x + y
let add5 = add 5              // a function still waiting for y
let eight = add5 3
> let add5 = add 5;;
val add5: (int -> int)

add5 is a function waiting for its second argument. Applying a function to only some of its arguments is called partial application. Functions that take their arguments one at a time like this are called curried, after the logician Haskell Curry. In F#, every function with several parameters is curried.

Function application groups to the left, which is the mirror image of the arrows: add 5 3 means (add 5) 3. First add 5 produces a function; then that function is applied to 3.

Partial application is useful whenever the first arguments describe a kind of job and the last one is the data:

let twoTo = power 2.0         // int -> float: powers of two
let kilo = twoTo 10           // 1024.0

And here is the promise from Week 1: printfn with a format string is a function waiting for the values to print:

let say = printfn "Hello, %s!"   // string -> unit
> let say = printfn "Hello, %s!";;
val say: (string -> unit)

F# reads the %s in the format string and works out that say needs a string. %d would ask for an int, and %f for a float. A mismatch is a type error, caught before the program runs.

TipPut the “setting” parameters first

Because of partial application, parameter order matters. Put the parameters that stay the same across many uses first, and the one that varies last. power x n with x first lets you make twoTo = power 2.0. If n came first, you could make “the cube of any number” instead. Choose the order that makes the useful partial applications possible. This matters a lot from Week 5 onward.

6.2 Generic types

Some functions don’t care what type their argument has:

let identity x = x
let first x y = x
let alwaysZero _ = 0
> let identity x = x;;
val identity: x: 'a -> 'a

> let first x y = x;;
val first: x: 'a -> y: 'b -> 'a

> let alwaysZero _ = 0;;
val alwaysZero: 'a -> int

A name starting with an apostrophe, like 'a (read “alpha”, or just “a”), is a type variable. It stands for any type. identity: 'a -> 'a works for int, string, or anything else, and the type promises that the result has the same type as the argument. first: 'a -> 'b -> 'a takes two arguments of possibly different types and returns something of the first one’s type. Such functions are called generic (the technical term is parametric polymorphism).

A generic type says a lot about what a function can do. A function of type 'a -> 'a knows nothing about its argument: it can’t add to it, print it, or compare it. So all it can do is hand it back. The type alone tells you what identity does.

Parentheses in a type mark a parameter that is itself a function:

let twice f x = f (f x)
let plus2 = twice (add 1)
> let twice f x = f (f x);;
val twice: f: ('a -> 'a) -> x: 'a -> 'a

twice takes a function f (of type 'a -> 'a) and a value x, and applies f two times. twice (add 1) is a function that adds 2. Functions that take or return functions are called higher-order functions; they are the subject of Week 5.

6.3 Working out a type by hand

F# finds types by looking at how each parameter is used. You can do the same thing, with a small method:

  1. Unknowns — Give each parameter, and the result, a placeholder type.
  2. Clues — Go through the body. Each use of a parameter is a clue: x + 1 means x is an int; x > 0 too; s + "!" means s is a string; an if condition is a bool; both branches of an if or all rules of a match have the result type.
  3. Combine — Put the clues together. If two clues disagree, that’s a type error.
  4. Generalise — Any placeholder with no clues at all stays generic: 'a, 'b, …

Example. let pick x y = if x > 0 then y + 1 else y * 2

  • Unknowns: x : ?1, y : ?2, result ?3.
  • Clues: x > 0 compares x with an int, so ?1 = int. y + 1 gives ?2 = int, and that branch has type int, so ?3 = int. The else branch y * 2 is also int, which agrees.
  • Result: pick: x: int -> y: int -> int.

Example. repeat from the ladder:

  • match n with | 0 -> … compares n with 0, so n : int.
  • The first rule’s result is "", so the result type is string.
  • The second rule is s + repeat s (n - 1). The result is a string, and + needs both sides to have the same type, so s : string.
  • Result: repeat: s: string -> n: int -> string.

6.4 When F# needs help: type annotations

Occasionally the clues aren’t enough, and you add the type yourself with a type annotation: (name: type) for a parameter, or : type after the parameters for the result.

Number types. As we saw in Week 1, when nothing decides between int and float, arithmetic assumes int. An annotation settles it:

let squareF (x: float) = x * x
let cube x : float = x * x * x      // annotate the result instead

Methods and properties. To look up .Length or .ToUpper() on a value, F# must already know the value’s type at that point:

> let len s = s.Length;;

  let len s = s.Length;;
  ------------^^^^^^^^

error FS0072: Lookup on object of indeterminate type based on information prior
to this program point. A type annotation may be needed prior to this program
point to constrain the type of the object.
let shout (s: string) = s.ToUpper() + "!"

Annotations are also useful as documentation, even when F# doesn’t need them. Writing the type first, as step 1 of the recipe suggests, and then letting the compiler confirm it, is a good habit.

7 Beyond F#

Pattern matching has spread to most modern languages, though the details differ:

Language Factorial by cases
Haskell fact 0 = 1 and fact n = n * fact (n - 1): literally the equations
Rust match n { 0 => 1, n => n * fact(n - 1) }
Kotlin when (n) { 0 -> 1; else -> n * fact(n - 1) }
C# n switch { 0 => 1, _ => n * Fact(n - 1) }
Java (21+) switch with patterns and when guards
Python (3.10+) match n: with case 0: and case _:

Two caveats when you use recursion in these languages. First, many of them limit recursion depth much more strictly than .NET does: Python stops at about 1000 nested calls by default. Recursion is still the right way to think about many problems, but for long-running repetition in those languages you may need a loop. (Week 7 shows how F# avoids the problem.) Second, they differ in how carefully they check that your cases are complete: Rust and Kotlin insist on it, Java and C# check it for some kinds of switch (C# gives a warning, as F# does), and Python doesn’t check at all.

Currying is the default in F#, OCaml, and Haskell. Elsewhere you can simulate it with a function that returns a function, such as const add = x => y => x + y; in JavaScript, or use a helper such as Python’s functools.partial. The idea, fixing some arguments now and the rest later, is useful everywhere.

Type inference. Rust, Kotlin, TypeScript, Swift, and C# infer the types of local variables, but require you to write the types of function parameters. F#, OCaml, and Haskell infer parameter types too, using the method from this week (known as Hindley–Milner type inference). That’s why F# code can look as light as a scripting language while being fully type-checked.

8 Going further (optional)

NoteWhy does a recursive function stop?

Step 4 of the recipe asks whether each call gets “closer to the base case”. This can be made precise. Find a measure: a natural number, computed from the arguments, that gets strictly smaller with every recursive call. For fact it is n; for binary it is also n (halved each time); for digitSum it is the number of digits; for gcd it is the second argument b. Since natural numbers can’t decrease forever, the recursion must stop. If you can’t find a measure, be suspicious. Some functions have no known measure at all. The Collatz function in this week’s lab is a famous example: nobody has ever proved that it stops for every input.

NoteProving a recursive function correct

The recipe’s “trust the smaller call” has a formal version: mathematical induction. Claim: sumTo n = \dfrac{n(n+1)}{2} for every n \ge 0.

  • Base case. sumTo 0 = 0, and \frac{0 \cdot 1}{2} = 0.
  • Step. Assume the claim holds for n - 1, that is, sumTo (n - 1) = \frac{(n-1)n}{2}. Then \texttt{sumTo } n = n + \frac{(n-1)n}{2} = \frac{2n + n^2 - n}{2} = \frac{n(n+1)}{2}.

That’s the whole proof. The structure of the proof follows the structure of the function exactly: one part per rule of the match. This connection between recursion and induction runs through all of functional programming.

NoteFunctions that call each other

Two functions can be defined in terms of each other, joined with and:

let rec isEven n =
    match n with
    | 0 -> true
    | n -> isOdd (n - 1)
and isOdd n =
    match n with
    | 0 -> false
    | n -> isEven (n - 1)

This is called mutual recursion. It is not a practical way to test evenness (n % 2 = 0 is better), but the pattern is useful for problems that have two kinds of case feeding into each other, such as parsers.

9 Summary

  • A recursive function calls itself on a smaller input; it needs let rec.
  • The recipe: type, base case, recursive case (trust the smaller call), check (trace, and make sure the input really gets smaller).
  • match writes case analysis as rules, | pattern -> expression, tried top to bottom. It often mirrors the math definition directly.
  • Patterns this week: constants, names, _, or-patterns, and when guards. F# warns about incomplete matches (FS0025) and unreachable rules (FS0026).
  • Recursion goes wrong when the base case can’t be reached (stack overflow), and int arithmetic overflows silently past about 2.1 billion.
  • a -> b -> c means a -> (b -> c): functions are curried, and partial application gives a function waiting for the rest.
  • 'a is a type variable; generic functions work for any type, and their types limit what they can do.
  • Work out a type by collecting clues from how each parameter is used; add an annotation when the clues aren’t enough.
